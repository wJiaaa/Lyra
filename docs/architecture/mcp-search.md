# MCP 工具延迟加载：`mcp_search` 与 `mcp_call`

MCP 工具多了以后，不放进发给服务商的工具表。系统提示词里有一份目录，每台服务器一行，模型要用时先
`mcp_search` 拿回完整 schema，再用 `mcp_call` 调用。代码在 `packages/core/src/tools/mcp-search.ts`。
MCP 那一侧的细节（3,000 token 阈值、常驻开关、目录里的服务器行、评测）见
[MCP 客户端](mcp-client.md#延迟加载)。

**内置工具一律常驻，不走这条路。** 2026-10-12 试过把其中几件延迟，量下来不划算，结论和数字在
[下面](#内置工具为什么不延迟)。以后想重做之前，先看那一节。

## 怎么做

- **被延迟的仍在这一轮的工具里。** 会话（`SessionCapabilities.composeTools` → `planTools`）给它们
  一个带 `deferred` 的副本。权限档、子代理定义、`sessionOnly` 这些按名字筛工具的地方照旧筛这些副本，
  筛剩下的才搜得到、调得到。
- **发出去的工具表只有一个出处**：`toolTable(available)`，也就是没延迟的那些，加上两个入口
  （有东西被延迟时）。请求（`loop.ts`）、日志里记的上下文（`session-turn.ts`、子代理）、
  「没有这个工具」的提示，三处读的都是它。两个入口是模块常量，描述里不点任何一件工具，所以
  每一轮都是同一串字节。
- **目录**在系统提示词里，标题是 `## MCP tools to search for`，一台服务器一段（`deferred:mcp:<id>`）。
  服务器增减走 `prompt/update.ts` 的增量，追加在历史末尾，不改写开头的 system。
- **调用**：`agent/tool-run.ts` 在计划阶段用 `routeMcpCall` 把 `mcp_call`，或者直接按名字叫的
  被延迟工具，换成真正的那个工具，参数先按 schema 校验（`tool-schema-check.ts`，ajv）。之后的
  钩子、审批与 PermissionRequest、技能的 `allowed-tools`、执行模式、结果预算，都和工具表里的工具
  走同一条路；`tool_start` 和工具结果上记的也是真名。`mcp_search` 不受技能的 `allowed-tools` 限制，
  因为它只是读说明书。换过去的调用，参数原文（`argumentsText`）也换成真参数的：留着外层
  `{tool, arguments}` 的原文，无参工具的 `arguments: {}` 会被「JSON 没解析出来」那道检查拦下
  （评测里三个模型都撞上过，每次要试 2–4 次）。
- **界面**：对话里经 `mcp_call` 的调用按真正那个工具画（`lib/tool-summary.ts` 的 `routedBlock`）。
  被校验退回的那次仍以 `mcp_call` 留着。

## 缓存实测

单元测试（`mcp-search.test.ts`）只证明请求前缀逐字节不变。2026-10-12 用服务商返回的
cacheRead 量了一遍：`test/tool-eval/mcp-cache-eval.ts`，30 台假服务器，一个会话 5 轮——Linear
（`mcp_search` + `mcp_call`）→ Slack → **新增** Twilio 后用它 → **移除** Notion 后查 Sentry → 不用
MCP 收尾。会话照 `session-turn.ts` 拼：提示词第一轮冻结，目录变化作为增量接在末尾，带前缀指纹、
日期块、剪枝器和缓存路由键。对照组同一剧本、30 台全部常驻。

「应读」是上一次请求的输入总量。下表只列每轮第一次请求（增减服务器就发生在这里），格式是
输入 / 应读 → cacheRead：

| 模型（协议） | | T2 | T3 +Twilio | T4 −Notion | T5 | 会话合计 输入 · 读到 |
| --- | --- | --- | --- | --- | --- | --- |
| deepseek-flash（Messages，官方端点） | 延迟 | 11,962 / 11,656 → 11,776 | 13,121 / 12,770 → 12,800 | 14,904 / 14,496 → 14,720 | 16,233 / 15,895 → 16,000 | 251k · 93.5% |
| | 常驻 | 38,741 / 38,453 → 38,528 | 39,429 / 39,030 → **35,968** | 38,278 / 38,278 → **26,368** | 38,851 / 38,540 → 38,656 | 581k · 90.4% |
| deepseek-flash（Responses，中转） | 延迟 | 11,902 / 11,618 → 11,520 | 13,614 / 13,099 → 13,056 | 15,166 / 14,453 → 14,336 | 17,739 / 17,155 → 17,152 | 259k · 92.7% |
| | 常驻 | 38,677 / 38,454 → 38,400 | 39,310 / 38,944 → **35,968** | 38,306 / 38,306 → **26,368** | 39,235 / 38,820 → 38,784 | 658k · 91.4% |
| gpt-6.1-sol（Responses，中转） | 延迟 | 8,159 / 8,110 → 7,936 | 8,632 / 8,408 → 8,320 | 9,121 / 8,919 → 8,448 | 9,525 / 9,460 → 9,216 | 113k · 81.7% |
| | 常驻 | 23,339 / 23,312 → 23,040 | 23,652 / 23,460 → **0** | 22,694 / 22,694 → **0** | 22,849 / 22,782 → 0 ¹ | 209k · 44.1% |

- **延迟组：增减服务器那一次没有断。** 增量接在末尾，上一次请求的整段输入照样读到，没读到的只有
  增量本身和新消息。三个模型其余各次也都在上一次输入的 128 token（DeepSeek 64）取整之内，
  只有 gpt-6.1-sol 差得多一些，最多 471 / 669 token（两次跑），都在诊断的 1,024 噪声线以内。
- **常驻组：增减服务器那一次断在工具表。** 本地前缀指纹报 `tools`。OpenAI 系整段从头重算（读到 0）；
  DeepSeek 从变了的那件工具起重算：Twilio 排在工具表靠后，丢 3k，Notion 排在中间，丢 12k。
- **服务商自己没读到的**：gpt-6.1-sol 走的中转站在本地前缀没变时偶尔回 0，两次延迟组各一次，
  位置不同（T3 第 2 次、T1 第 5 次）；常驻组 ¹ 也有一次。这和延迟加载无关，路由键已经在带
  （`ai/cache-routing.ts`）。
- **两家都不报 cacheWrite**（DeepSeek 的 Anthropic 端点回 0，OpenAI 系本来就没有），写入那一侧量不到。
- **Chat Completions 没量**：本机没有配走这条协议的模型。这条协议只有单元测试的前缀断言。
- 合计里的命中率被冷启动和中转站回 0 那几次拉低；延迟组去掉这几次，读到的是输入的 95–97%、
  应读的 97–100%。同一次跑的两组相比，延迟组每个会话的输入是常驻组的 39–54%。

## 内置工具为什么不延迟

2026-10-12 把 `preview`、`image_generate`、`learn`、跨会话三件、浏览器五件做成可延迟，走同一套
`mcp_search` / `mcp_call`，量完以后全部撤回。

**省得太少。** 本机会话（`toolTokens` 的 3.5 字符估，Anthropic 编码）：

| | token |
| --- | --- |
| 桌面端全部 28 件工具 | 7,403 |
| 6 件（`preview` 1,149、`image_generate` 376、`learn` 285、跨会话三件 608）合计 S | 2,363 |
| 两个入口 + 目录行 + 「去 `mcp_search` 拿」的提示，开销 O | 655 |
| 每次请求净省 S − O | 1,708 |

按 MCP 阈值用的同一个模型（缓存读按一成，平均每个会话 24.1 次请求）：

| | 每个会话（token 当量） |
| --- | --- |
| 省：1,708 × 0.1 × 24.1 | ≈ 4.1k |
| 省：序列开头那次写入，1,708 × 1.25 | ≈ 2.1k |
| 花：每发现一次多一次请求（0.1 × 上下文 ≈ 10k）加搜索结果（0.3k–2.0k），每会话 0.21 次 | ≈ 2.4k |
| **净省** | **约 3.8k**（算上 14% 缓存未命中，最多约 11k） |

一个会话的总花销以十万到几十万 token 当量计，这只有 1–2%。

**浏览器那组是净亏。** 五件约 0.7k，延迟着每个会话只省约 2.7k。试过「这个会话一有浏览器标签，
就从下一轮起回到工具表」，换表那一下前缀从工具表起整段重算一次（真窗口实测工具表 16,623 →
18,996 字符，断在 `tools` 段），代价约 1.15 × 当时的上下文（本机中位 85k），摊到每个会话约 5.8k，
比省下的还多。不切回，就是每次用都多一次搜索。

**`preview` 有准确率风险。** 它不只是画图：模型写完页面用 `preview` 的 `check` 截图自检。藏起来以后，
用它多一步，模型可能干脆少做这一步自检，交出去的页面就没被看过。下面的评测每题只跑 2 次，量不出
这种差别。

**评测**（`test/tool-eval/mcp-search-eval.ts` 当时的版本，7 个内置任务各跑 2 次；平均输入是各次请求的
input + cacheRead + cacheWrite 之和，没按缓存折价）：

| 模型（协议） | 内置延迟 | 内置全常驻 |
| --- | --- | --- |
| deepseek-flash（Responses） | 13/14 · 3.50 次 · 33.5k | 14/14 · 3.00 次 · 40.7k |
| deepseek-flash（Messages） | 14/14 · 3.79 次 · 43.5k | 13/14 · 3.00 次 · 36.5k |
| gpt-6.1-sol（Responses） | 14/14 · 3.64 次 · 26.4k | 14/14 · 2.50 次 · 21.9k |

通过率两边一样，用到被延迟的工具时每题多 0.5–1.1 次请求。差别在噪声里，撑不起上面那点节省之外
的风险。

**以后想重做，先回答这几件事**：一件工具的 schema 要大到每会话净省明显超过 1–2%；它不能是模型
自检、找回原文这类「少做一步就伤准确率」的工具（`preview`、`recall`、`lsp`）；它不能在会话中途
因为用法回到工具表。

## 为什么不用原生路径

- **Anthropic 的 `defer_loading` + `mcp_search`，以及对话中途的 `tool_addition`。** 只有部分 Claude
  型号支持，要 beta 头；本机配的 6 个服务商没有一个直连 `api.anthropic.com`，都是中转或兼容端点，
  beta 头和这些块过不过得去没有保证，过不去就是整轮报错。原生搜索的结果块要在历史里原样回放，
  压缩、子代理、侧聊、撤回都得认识它。通用路径的前缀已经逐字节不动，原生路径在这里省不下什么。
- **DeepSeek。** 官方文档（Anthropic 兼容页的字段表、tool calls 页）没有 `defer_loading`、
  `tool_addition`、`tool_reference`，`anthropic-beta` 在 `/messages` 上标的是忽略。deepseek-harness
  给 `deepseek-flash` 开了 `addition-only`，依据是一个没有留存结果的 e2e；不是公开能力，不接。
- **maka 的做法**（搜到的工具激活进工具表、轮末撤掉）：工具表在前缀最前面，每一轮用到延迟工具就
  加一次、撤一次，整段前缀重算两次——真实会话里这一段是 15–45k token。这里一次搜索只往末尾追加
  约 1k token。它的好处是参数由服务商按 schema 约束；这边用执行前校验补上。
- 压缩的摘要请求从上一次主请求分叉（`runtime/compaction/compaction-fork.ts`），工具段原样取自发出去的那一次
  （`stream-turn.ts` 记下的 `toolTable` 结果），两个入口照样在、被延迟的照样不在，前缀对得上；退回
  独立请求时发 `tools: []`。

## 已知上限

- 搜索是关键词打分，不是语义检索。说法和工具名、描述一个词都不沾时，要靠模型换个词再搜。
- 很少有服务器在 `initialize` 里给描述，目录里多数服务器只有名字和工具名。
