# Agent 循环：每条恢复与停止路径为什么是这样

代码在 `packages/core/src/agent/`：

| 文件 | 回答的问题 |
| --- | --- |
| `run-config.ts` | 一次运行拿到什么、交回什么（`AgentRunConfig` / `AgentRunResult` / `LiveModel`） |
| `loop.ts` | 还要不要再来一轮：插话、模型切换、压缩、恢复、收尾判断 |
| `stream-turn.ts` | 一个请求怎么变成一条落定的回复：重试计数、换模型放手、拒收挂起 |
| `tool-run.ts` | 一轮里的工具怎么跑：并行/串行、审批、钩子、停止不等工具 |
| `repetition.ts` | 这一轮有没有在原地打转（阈值的来历写在那个文件顶上） |

代码里的注释只留「这里必须这样、改坏过的是哪种写法」。演进和论证在这里。成本与停止机制的
实测数字见 [agent-cost-and-stopping.md](agent-cost-and-stopping.md)，模型切换的决定见
[ADR-0025](../adr/0025-model-switch-applies-from-next-request.md)。

## 一轮的顺序

`runAgent` 每一轮按这个顺序走，每一步是一个函数：

1. `takeSteering`：把上一轮留下的和队列里新来的插话放进历史。
2. `prepareHistory`：换模型 → 剪枝 → 压缩。
3. `requestReply`：发请求；被拒收或超长时各恢复一次。
4. 回复出错或中断：`closeUnansweredCalls` 后收场。
5. 没有工具调用：`endWithoutTools` 决定收场还是再来一轮。
6. 有工具调用：`runToolTurn` 跑工具，再由 `answerRepeats` 处理重复。

凡是运行时以用户角色说的话（续写、催促、重复提示）都走 `inject(synthetic(...))`：用户角色是
模型唯一会当作指令接收的角色，而 `synthetic` 让界面不把它画进人的气泡——画进去，转录里就是人
在要求他从没要求过的东西。

## 模型中途切换

`provider` / `model` 是开轮时的那个。从前整轮都用它：人在一轮中途换了模型，剩下的几十个请求照旧
发给旧的；旧上游坏了、正在一刻不停地重试时，换模型等于没换——界面上写着「Model B」，服务器收到的
一直是 a（`e2e/edit-resend-model-probe.ts` 量出来的）。重试策略早就是每次重试前现读的
（`RetryPolicySource`），模型是同一个道理。

- **只在循环顶上换。** 一个请求发出去之后它就是它。唯一例外是还什么都没说出口的请求（在连、在
  重试）：`stream-turn.ts` 用单独的 `switchAbort` 放手它，因为它的意思是「换个人重来」，不是「停」，
  不能和人按停止的 `signal` 混在一起。已经在出字的不动。
- **光靠每轮开头读一次不够**，所以 `LiveModel` 有 `onChange`：那个正在重试的请求可能要等很久才到
  下一轮，而人换模型恰恰是因为它。
- **被放手的请求不算一轮。** 算进去等于让人为换模型付一轮的检查点额度。没开始出流的什么都不发、
  不进转录——留一条空的「已停止」会让人以为自己按了停。重试过的，那行「正在重连」要收场，而且说
  实话：`retry_settled` 的 `outcome` 是 `switched`，不是 `recovered`。
- **按「切换那一刻之前的都剥」摘供应商句柄**，不按每条消息的 `model` 字段比：有的供应商回报的模型
  名和配置对不上（带日期、带别名），逐条比会把同一个模型自己的思考签名也剥掉。
- **`adopted`**：人按下切换和循环真正换过去之间，旧模型可能又说完了一句，那一句的句柄同样不能交给
  新模型，所以会话把「换模型的位置」挪到循环真正换过去的那一刻。

## 请求被拒收：剪掉最大的东西，再问一次

4xx 不是传输故障，没有谁会重试它——这是对的，同一个问题问两遍得到同一个答案。麻烦在于问题是
*历史*，而历史不会自己变：之后每个请求都带着同一份被拒的负载，于是对话不只是失败，是被封死。
重试失败，继续失败，明天打开还是失败。

一个工具结果常常就是全部原因——一份 `gh api` 输出、一个两千行的文件、一次扫到构建目录的 grep——
而在格式之间转译的网关各有限制和 bug，客户端无法穷举。所以不去猜是哪一种，把过大的结果各压成一行
再问一次。已经输掉的那种情况多花一个请求，其余情况一分不花。

判断读的是失败分类（`failure.hint === "check-request"`），不读 `errorMessage` 的措辞：那行字
是给人看的，措辞一变，模式匹配就悄悄失效。401 是密钥、404 是地址、429 是排队，都不会因为历史变短
而变好，所以范围刻意收窄。

## 上下文超长：强制压缩一次，再发一次

80% 的自动压缩线挡住大多数，挡不住的是估算偏低（中文、密集 JSON）和一次涨太多（一个巨大的工具
结果）。剪掉过大的输出是便宜的第一步，上面已经试过；还是超长、或没东西可剪，就只剩压缩——不压，
这段历史下一轮原样再发，会话卡死在这里。

每轮最多一次，由结构保证：重发的结果不会再回到这段判断。压缩失败、没压小、压完还超长，都照原
错误收场。压缩走的是和轮首相同的 `compactStep`，剪枝视图的持久化、边界事件、界面进度是同一套；
压缩之后重复计数清零（早先的原文进了摘要，再读一次是在拿回来，不是在打转）。压缩自己抛错时，先把
被拒的那条提交再往上抛：转录里要留得下这一轮为什么停。

## 被拒的回复先挂起（`held`）

被拒收的那条错误回复在决定恢复与否之前不提交（不发 `message_end`）。调用方要么恢复后重发、
`discard` 掉它，要么放弃恢复、`commit` 它。

先提交再重发的话，日志里多出一条循环眼里没有的失败回复。压缩边界按「最后 N 条」从日志末尾数，
数偏一条，下一轮重建出的历史就和刚发出去的不一样，还可能从一对工具调用中间切开。

`discard` 时，已经画出来的那一截用 `message_discarded` 收掉；重连过的那行要收场（这个请求确实
没救回来）；一次都没重试过的不再报一条失败——紧接着的重发才是结果。

## 没说完的工具调用必须有回答

回复中途断开（断网、被停止）时会留下已经开了头的工具调用。Anthropic 拒绝任何后面没有
`tool_result` 的 `tool_use`——所以一个孤儿结束的不是这一轮，而是整个对话：之后每个请求都撞同一个
400，包括想把工作接回来的那个。这些调用一律判失败而不执行：写到一半就停止到达的参数不是参数。

撞上输出上限时同理：流里的参数可能能解析，但缺字段，执行它比判它失败更糟。

## 撞上输出上限

输出上限已取到模型允许的最大值（`contextMaxTokens`），没有更大的可调。纯文本回复被截断时不当作
答完：从前直接 `done`，界面上是一段戛然而止的回答，看不出被截断。现在让它从断处接着写，连续
`MAX_TRUNCATED_REPLIES` 次还在撞就停，并说出来。工具参数被截断时让它拆小重发，连续撞满同样停下。

## 空回复与 Stop 钩子

一份清单分不清「在提问」和「放弃了」。有正文就交还给人；只有真正空的回复才有限次催促
（`MAX_NUDGES`，工具调用不补充这个额度），用完报错。之后才问 `onStop`：Stop 钩子可以说「还没
做完，因为……」，它返回的消息注入后循环继续。

## 插话与步数上限

`drainSteering` 会清空队列，所以取出来的东西必须留在 `carried` 里；只读长度会把人的话丢掉，循环
却在没有新输入的情况下再问一次模型。

最后一次流式输出期间到达的插话仍然该得到回答，但**到了步数上限就不在收尾时取**：取走之后
`continue`，循环顶上先判上限、直接收场，这句话就既不在转录里也不在队列里了。留在队列里，由宿主
按「没人接走的插话」接着发——会话的 `drainPending`、子代理的 `runSubAgent` 都认这条路。

人说了新话会结束上一个 skill 的工具限制，否则会以一个他未必记得的 skill 名义，静默拒绝他刚要求
的工作。第一轮要把发起这次运行的那条提示也算上：状态表活得比一次运行长。

## 工具说「到此为止」

`ToolResult.terminate` 曾经一直存在却没人写也没人读，唯一需要它的 `yield` 只能靠模型自觉收尾。
`yield` 的语义是交付即结束：结果已经在 `state` 里，此后再问一句，答案没人读。

那一句的代价不是零。顺利时是一整份上下文换一句「我做完了」；不顺时模型无话可说、服务商转成一个
没有内容的流，就是一次空回答，而空回答会被重试。开着无限重试时这一轮永远转下去：真实日志里量到
过同一个请求重发 222 次、34 分钟。收在 `turn_end` 之后：这一轮完整发生过，只是不再问下一句。
出错的 `yield`（校验没过）不算终止，那是「重填一次」。

## 重复：先纠正，纠正无效才停

这里原本是「问满六次就结束」。停下来既没告诉模型该怎么办，也没把等结果的人放出来，只是把一次
卡住变成一次中断。现在：

- **第三次起不再重贴原文**，只回一句「这是第 N 次，结果没变」。真实日志里同一段 `read` 贴过 5 遍，
  同一个 `skill` 注入过 4 次，每次 5,625 token。只换给模型看的那份，工具照常执行——结果真变了，
  指纹就不同，根本走不到这里。
- **原文必须真的还在眼前。** 计数只在改动工作区、压缩时清零，而剪枝会把早先那几份换成回查指针；
  那时再把这份也换掉，模型手里一份原文都没有，所以这份留着。
- **换在提交之后。** 日志和界面留原文，代价是重启后重建的历史在这条上和当时发出去的不同，前缀从
  这里断一次。换到提交之前，要么等整批跑完才落盘（崩溃时丢掉已完成的结果），要么让计数看到的
  不是原文，都不划算。
- **两条线两句话。** 对一个每轮都在改 `offset` 的调用说「你用了同样的参数」，模型对照一眼就知道
  不成立，连带后半句一起不信。真实记录里一次翻了 37 页的搜索全程没收到提示，收到时那句话描述的也
  不是它在做的事。
- **`RepetitionWatch` 跨整条续跑链共用一只**，由调用方给。每次调用新建一只，计数在续跑时清零：
  真实日志里那个会话跑了 588 轮、起停五次，每一段都以为自己是第一段。

阈值和误伤记录见 `repetition.ts` 顶部和
[agent-cost-and-stopping.md](agent-cost-and-stopping.md)。

## 单个请求里的几件小事

- **重试按请求计数。** `fetchWithRetry`（拿连接）和 `retryStream`（保连接）嵌套，各自从 1 数，
  直接透传时屏幕上数成 1、2、1、1、2，第五次尝试被叫成「第 1 次」。人在等的是这个请求。
- **`retry_settled` 必须说。** 它是唯一同时知道「重试了几次」和「最后那条什么样」的地方；少了它，
  「正在重连」没有下文，「重连成功」和「窗口闲着」长得一样。一次都没重试过的**失败**（密钥错、
  模型名错，分类器判 `fatal` 当场停）也要说，否则界面上只剩一片安静。
- **前缀指纹**写在回复上，作为缓存未命中的归因证据（`ai/prefix-fingerprint.ts`）。基准只从缓存
  诊断也算数的请求推进（`requestPrompt`），两边比的是同一对请求。
- **`AgentRunResult.view`** 是模型眼里的整段历史（压缩、剪枝之后）。子代理续跑从它往后接，前缀才
  逐字相同；从转录重建会丢掉压缩边界、挪动日期块，缓存从第二条起全部作废。
- **`environment`** 给主会话用：它的历史每轮从日志重建，日志里没有日期块；渲染只看消息自己的时间
  戳，同一份历史每次得到同样的字节。子代理不开，它存的就是带日期块的 `view`。
