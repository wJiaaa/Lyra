# Agent 循环：每条恢复与停止路径为什么是这样

代码在 `packages/core/src/agent/`：

| 文件 | 回答的问题 |
| --- | --- |
| `run-config.ts` | 一次运行拿到什么、交回什么（`AgentRunConfig` 的四组 / `AgentRunResult` / `LiveModel`） |
| `loop.ts` | 一轮怎么走：插话、模型切换、压缩、恢复，再按收尾规则表问下去 |
| `turn-checks.ts` | 一条回复处理完以后还要不要再来一轮：续写、催促、Stop 钩子、清单、重复、`yield`，按优先级排成两张表 |
| `stream-turn.ts` | 一个请求怎么变成一条落定的回复：重试计数、换模型放手、拒收挂起 |
| `tool-run.ts` | 一轮里的工具怎么跑：并行/串行、审批、钩子、停止不等工具 |
| `repetition.ts` | 这一轮有没有在原地打转（阈值的来历写在那个文件顶上） |
| `plan-watch.ts` | 清单相关的三句话：单独调清单、跑久了问进度、收尾时清单没勾完 |

代码里的注释只留「这里必须这样、改坏过的是哪种写法」。演进和论证在这里。成本与停止机制的
实测数字见 [agent-cost-and-stopping.md](agent-cost-and-stopping.md)，模型切换的决定见
[ADR-0025](../adr/0025-model-switch-applies-from-next-request.md)。

## 一次运行拿到的四组配置

`AgentRunConfig` 只有四个键，每组只给一类代码读（为什么这样分，见
[ADR-0034](../adr/0034-run-config-in-four-groups.md)）：

| 组 | 装什么 | 谁读 |
| --- | --- | --- |
| `session` | 会话 id、system prompt、历史、状态图、日期块、压缩、剪枝器、artifact 存放处 | loop、`compact-step.ts` |
| `model` | 供应商与模型、换模型、思考等级、缓存键、重试、请求替身、请求观察 | `stream-turn.ts` |
| `tools` | 工具表、`env`（原样交给每次调用的 `ToolContext` 部分）、审批、三个工具钩子 | `tool-run.ts` |
| `control` | 停止信号、插话队列、Stop 钩子、重复检测、轮数上限 | loop |

- **一个字段只属于一组。** 停止信号归 `control`、状态图和会话 id 归 `session`，但 `stream-turn`
  和 `tool-run` 也要用：由 loop 作为参数交下去（`StreamScope`、`ToolRunScope`），不在第二组里再放
  一份。`run-config.ts` 里有编译期断言，两组出现同名字段、或者顶层多出第五个键，`tsc` 都会失败。
- **组内字段必须写出来。** 除了有通用默认值的几个数（`maxTurns`、`maxTokens`、`temperature`、
  `retryAttempts`），每个字段都是必填的，没有就写 `undefined`。`tools.env` 由 `ToolContext` 推导：
  给工具加一个上下文字段，主会话、子代理、侧聊三处构造都会编译失败，直到各自写明给什么。
- **继承和覆盖按组写。** 子代理讨交接那一轮是 `{ session: { ...runConfig.session, messages }, model:
  runConfig.model, tools: { 同一张表，除 yield 外一律拒绝执行 }, control: { 两轮 } }`；主会话续跑只换
  `session.messages`。工具表不能换：工具定义排在请求最前面，换掉它前缀缓存从第 0 字节起作废。
- 测试不做类型检查，统一经 `packages/core/test/run-config.ts` 的 `runConfig()` 构造，没提到的字段都是
  `undefined`。

## 一轮的顺序

`runAgent` 每一轮按这个顺序走，每一步是一个函数：

1. `takeSteering`：把上一轮留下的和队列里新来的插话放进历史。
2. `prepareHistory`：换模型 → 剪枝 → 压缩。
3. `requestReply`：发请求；被拒收或超长时各恢复一次。
4. 回复出错或中断：`closeUnansweredCalls` 后收场。
5. 没有工具调用：`endWithoutTools` 先收插话，再按 `afterProse` 表问下去，第一条有意见的规则说了算。
6. 有工具调用：`runToolTurn` 跑工具，再按 `afterTools` 表问下去：`end` 立刻收场，`say` 照说、后面的照问。

两张表在 `turn-checks.ts`，表里的顺序就是规则之间的优先级。加一条收尾规则是写一个函数、在 `turnChecks` 里登记一行，
不用改 `loop.ts`；改了顺序要说清楚理由，`turn-checks.test.ts` 守着写明了理由的那几条。

凡是运行时以用户角色说的话（续写、催促、重复提示）都走 `inject(synthetic(...))`：用户角色是
模型唯一会当作指令接收的角色，而 `synthetic` 让界面不把它画进人的气泡——画进去，转录里就是人
在要求他从没要求过的东西。

## 会话正忙时说的话

`AgentSession.prompt` 的 `deliver` 决定一句话在会话正忙时怎么进去，闲着时三种都是开一轮：

- `followUp`：排到这一轮之后，另开一次运行。桌面端忙时回车走的是自己的排队条（`store/queue-slice.ts`），
  这一轮干净收尾（`agent_end` 的 reason 是 done）才发下一条。
- `steer`：插进这一轮，由第 1 步 `takeSteering` 在下一个请求之前取走，打上 `steered`。要等模型写完
  手上这一步，可以是好几分钟，所以不做成给人按的按钮；只有运行时自己（主会话在等子代理时把队首
  送进去）和声明了 `deliver: steer` 的命令用它。
- `interrupt`：排队条上的「现在就发」。调停止按钮那一套 `abort()`，等会话完全放手
  （`SessionActivity.quiet`），再把这句话作为新的一轮提交，打上 `interrupting`。被停下的回复写到哪儿
  留到哪儿（`stopReason: "aborted"`），没跑完的工具照停止时那样补上取消的结果，下一次请求模型都读得到。

`steered` 和 `interrupting` 的话发给模型时由 `prompt/steering.ts` 套一层说明：在你工作时发来的；后者
还说明上一条回复因此停在半截、照这句话的意思决定接不接着做。说明只在请求拼装时加，不进转录。
桌面端把被打断那一轮的 `agent_end` 认作交接而不是停止（`store/handoff.ts`），中间不闪「已暂停」。

## 模型中途切换

`provider` / `model` 是开轮时的那个。从前整轮都用它：人在一轮中途换了模型，剩下的几十个请求照旧
发给旧的；旧上游坏了、正在一刻不停地重试时，换模型等于没换——界面上写着「Model B」，服务器收到的
一直是 a（`e2e/edit-resend-model-probe.ts` 量出来的）。重试策略早就是每次重试前现读的
（`RetryPolicySource`），模型是同一个道理。

- **只在循环顶上换。** 一个请求发出去之后它就是它。唯一例外是还什么都没说出口的请求（在连、在
  重试）：`stream-turn.ts` 用单独的 `switchAbort` 放手它，因为它的意思是「换个人重来」，不是「停」，
  不能和人按停止的 `signal` 混在一起。已经在出字的不动。
- **光靠每轮开头读一次不够**，所以 `LiveModel` 有 `onChange`：那个正在重试的请求可能要等很久才到
  下一轮，而人换模型恰恰是因为它。
- **被放手的请求不算一轮。** 算进去等于让人为换模型付一轮的检查点额度。没开始出流的什么都不发、
  不进转录——留一条空的「已停止」会让人以为自己按了停。重试过的，那行「正在重连」要收场，而且说
  实话：`retry_settled` 的 `outcome` 是 `switched`，不是 `recovered`。
- **按「切换那一刻之前的都剥」摘供应商句柄**，不按每条消息的 `model` 字段比：有的供应商回报的模型
  名和配置对不上（带日期、带别名），逐条比会把同一个模型自己的思考签名也剥掉。
- **`adopted`**：人按下切换和循环真正换过去之间，旧模型可能又说完了一句，那一句的句柄同样不能交给
  新模型，所以会话把「换模型的位置」挪到循环真正换过去的那一刻。

## 请求被拒收：剪掉最大的东西，再问一次

4xx 不是传输故障，没有谁会重试它——这是对的，同一个问题问两遍得到同一个答案。麻烦在于问题是
*历史*，而历史不会自己变：之后每个请求都带着同一份被拒的负载，于是对话不只是失败，是被封死。
重试失败，继续失败，明天打开还是失败。

一个工具结果常常就是全部原因——一份 `gh api` 输出、一个两千行的文件、一次扫到构建目录的 grep——
而在格式之间转译的网关各有限制和 bug，客户端无法穷举。所以不去猜是哪一种，把过大的结果各压成一行
再问一次。已经输掉的那种情况多花一个请求，其余情况一分不花。

判断读的是失败分类（`failure.hint === "check-request"`），不读 `errorMessage` 的措辞：那行字
是给人看的，措辞一变，模式匹配就悄悄失效。401 是密钥、404 是地址、429 是排队，都不会因为历史变短
而变好，所以范围刻意收窄。

## 上下文超长：强制压缩一次，再发一次

自动压缩线（90%，小窗口更早）挡住大多数，挡不住的是估算偏低（中文、密集 JSON）和一次涨太多（一个巨大的工具
结果）。剪掉过大的输出是便宜的第一步，上面已经试过；还是超长、或没东西可剪，就只剩压缩——不压，
这段历史下一轮原样再发，会话卡死在这里。

每轮最多一次，由结构保证：重发的结果不会再回到这段判断。压缩失败、没压小、压完还超长，都照原
错误收场。压缩走的是和轮首相同的 `compactStep`，剪枝视图的持久化、边界事件、界面进度是同一套；
只有一处不同：这里不给分叉起点，摘要直接走独立请求——完整历史本来就放不下，从主请求分叉只会再被拒一次
（见[上下文组装](context-assembly.md#压缩请求从主请求分叉)）；
压缩之后重复计数清零（早先的原文进了摘要，再读一次是在拿回来，不是在打转）。压缩自己抛错时，先把
被拒的那条提交再往上抛：转录里要留得下这一轮为什么停。

## 被拒的回复先挂起（`held`）

被拒收的那条错误回复在决定恢复与否之前不提交（不发 `message_end`）。调用方要么恢复后重发、
`discard` 掉它，要么放弃恢复、`commit` 它。

先提交再重发的话，日志里多出一条循环眼里没有的失败回复。压缩边界按「最后 N 条」从日志末尾数，
数偏一条，下一轮重建出的历史就和刚发出去的不一样，还可能从一对工具调用中间切开。

`discard` 时，已经画出来的那一截用 `message_discarded` 收掉；重连过的那行要收场（这个请求确实
没救回来）；一次都没重试过的不再报一条失败——紧接着的重发才是结果。

## 没说完的工具调用必须有回答

回复中途断开（断网、被停止）时会留下已经开了头的工具调用。Anthropic 拒绝任何后面没有
`tool_result` 的 `tool_use`——所以一个孤儿结束的不是这一轮，而是整个对话：之后每个请求都撞同一个
400，包括想把工作接回来的那个。这些调用一律判失败而不执行：写到一半就停止到达的参数不是参数。

撞上输出上限时同理：流里的参数可能能解析，但缺字段，执行它比判它失败更糟。

## 撞上输出上限

输出上限已取到模型允许的最大值（`contextMaxTokens`），没有更大的可调。纯文本回复被截断时不当作
答完：从前直接 `done`，界面上是一段戛然而止的回答，看不出被截断。现在让它从断处接着写，连续
`MAX_TRUNCATED_REPLIES` 次还在撞就停，并说出来。工具参数被截断时让它拆小重发，连续撞满同样停下。

## 空回复与 Stop 钩子

一份清单分不清「在提问」和「放弃了」。有正文就交还给人；只有真正空的回复才有限次催促
（`MAX_NUDGES`，工具调用不补充这个额度），用完报错。之后才问 `onStop`：Stop 钩子可以说「还没
做完，因为……」，它返回的消息注入后循环继续。

## 清单跟着事走

两处：工作途中提醒，收尾时兜底。

- **工作途中**：按请求数计，连着 `PROGRESS_EVERY`（20）次请求没汇报进度，就在那一轮的工具结果之后插一句
  运行时的话，跟着下一次请求发出去，不单独占一次请求；说过就重新计数。什么算汇报看手上有没有没做完的
  清单（`PlanWatch.progress`）：
  - 有清单：只认 `todo_write`，嘴上说了不算，因为界面上那张清单不会因为它说了一句而往前走——`2333f4e9`
    每隔几轮就说一句，清单却从第 4 次请求停在 1/5 直到收尾。提示把整张清单念给它听（`stalePlanNote`）。
  - 没清单：对人说过话就算。提示只要一两句现状——在做什么、下一步做什么——并明说不必为此新建清单
    （`PROGRESS_NOTE`）。简单的活不需要清单，跑得久也不是要它补一份计划的理由。不问「做完了什么」，
    也明说不要阶段性结论：被问到时证据多半没收齐，`9db78fc1` 排查到一半答了一句错的定论，靠用户打断纠正。

  不接在工具结果末尾：那一轮最后一条常常是报错，`2333f4e9` 第 10 轮处重放三次，接在报错后面的提醒一次
  都没被读到；措辞要说「现在就对一遍、这次回复里带上」，说「下次顺手勾掉」五次里只照做一次。

  **只问，不停。** 2026-10-11 在本机 367 次运行上重放过「问过之后再 20 次请求还不汇报就停」：唯一会被
  叫停的是一场改了 30 次文件、196 个调用里 185 个指纹互不相同的真实工作（`c3b2b5f0`，deepseek-flash），
  和 `repetition.ts` 顶上记着的「60 轮不说话就停」是同一种误伤。同一次重放里，301 次运行在 20 次请求以内
  做完，从头到尾不会被问；原来按 10 轮念清单的那句要说 50 次，现在 40 次。
- **收尾兜底**：Stop 钩子放行之后，清单里如果还有 in_progress 的项，就问它一次（`openPlanNote`）。
  一轮都收尾了还说「正在做」，清单和事实自相矛盾；剩下的全是 pending，是它有意停在那一步前面（多半在
  等人确认），不问——真实模型上量过，那种情况问了也只是原样再交一遍清单。这不是替它续跑。起因是
  2026-10-10 的 `2333f4e9`：五步全做完，最后一条回复的思考里写着「Let me finalize the todos」，回复里
  却没有这次调用，清单停在 1/5，界面显示停在第 2 步。它如果只回了一次 `todo_write`，执行完就结束，
  不再要一段新正文，因为回答已经在上面了；桌面端因此要认得「回答之后补勾」这种结尾
  （`store/turn-stop.ts` 的 `beforePlanTick`），否则会当成被中断。一次运行只问一次。

## 停止与续跑总表

一轮为什么停、为什么还在跑，所有的线都在这张表里。改任何一条之前先跑 `pnpm audit:sessions`，改后再跑一次对照。

| 线 | 值 | 到了之后 | 在哪 |
| --- | --- | --- | --- |
| 一次运行的步数 | 200（子代理每段 60） | `max_turns`，交给续跑链 | `loop.ts` `DEFAULT_MAX_TURNS`、`sub-agent.ts` `SUB_AGENT_CHECKPOINT_TURNS` |
| 续跑次数 | 10 段 | 停下，通知「已达到自动续跑次数上限」 | `continuation.ts` `MAX_CONTINUATIONS` |
| 续跑没推进清单 | 连续 2 段一项没勾 | 停下，通知 `plan-stalled` | `continuation.ts` `STALLED_CONTINUATIONS` |
| 撞到步数上限时清单为空或已做完 | — | 主会话停下；子代理宽限一段让它写清单 | `continuation.ts` `planless` |
| 空回复 | 催 3 次 | `error`「模型连续返回空回复」 | `turn-checks.ts` `MAX_NUDGES` |
| 纯文本撞输出上限 | 续写 3 次 | 停下，通知 `output-limit` | `turn-checks.ts` `MAX_TRUNCATED_REPLIES` |
| 工具参数撞输出上限 | 连续 3 次 | `error`，让它拆小 | 同上 |
| 同一调用、同一结果 | 第 3 次起纠正，第 10 次停 | `stalled` | `repetition.ts` `REPEAT_WARN` / `REPEAT_STOP` |
| 翻页问同一个问题 / 切图测距 | 12 次 / 5 次 | 只提示，不停 | `repetition.ts` `INTENT_WARN` / `PROBE_WARN` |
| 没汇报进度 | 20 次请求 | 只问，不停 | `plan-watch.ts` `PROGRESS_EVERY` |
| 收尾时清单还有「正在做」 | 每次运行 1 次 | 问一次，不停 | `plan-watch.ts` `closing` |
| Stop 钩子要求接着做 | 3 次 | 之后不再理会钩子 | `hooks.ts` `MAX_STOP_HOOK_CONTINUATIONS` |
| 请求被拒收 / 上下文超长 | 各恢复 1 次 | 照原错误收场 | `loop.ts` `requestReply` |
| 请求重试 | 按设置页：网络默认无限、上游默认 10 次 | `error`；不在外面整轮重来，由人点「继续」 | `ai/retry.ts`，见 [retry-policy.md](retry-policy.md) |
| 授权卡片没人答 | 5 分钟 | 当作拒绝 | `approvals.ts` `UNATTENDED_TIMEOUT_MS` |
| `ask_user` 没人答 | 30 分钟 | 当作没有回答，要求它在回复里说出来 | `approvals.ts` `QUESTION_TIMEOUT_MS` |
| `yield` 交付 | — | `done`，不再问下一句 | `turn-checks.ts` `delivered` |

没有按花费或「多久没说话」停的线，两种都试过并拆掉了，见 `repetition.ts` 顶上。

## 计划模式：同一张工具表，开关开着时只放行只读

`SessionMeta.planMode` 开着的那一轮，`assembleTurn` 把工具表交给 `planModeTools` 包一层（`runtime/plan-mode.ts`）
并加上 `submit_plan`。schema 一个字节不变，只有 `execute` 在开关开着时按只读名单放行、其余拒绝；`bash`
只放 `isReadOnlyCommand` 认得的命令，并压进只读沙箱。`submit_plan` 走 `interactive` 审批卡片，批准那一刻
把状态图里的开关关掉、把步骤写进 `TODOS_KEY`——同一轮里下一次调用就直接放行，不用换表、不用等下一轮。
这条工具结果提交时会话把 meta 清掉（`recordTurnEvent`）。计划进 `task-context`，压缩后原样注入。
这一轮派出去的子代理拿到的是包过的表，开关是主会话的。设计取舍见 ADR-0044。

## 插话与步数上限

`drainSteering` 会清空队列，所以取出来的东西必须留在 `carried` 里；只读长度会把人的话丢掉，循环
却在没有新输入的情况下再问一次模型。

最后一次流式输出期间到达的插话仍然该得到回答，但**到了步数上限就不在收尾时取**：取走之后
`continue`，循环顶上先判上限、直接收场，这句话就既不在转录里也不在队列里了。留在队列里，由宿主
按「没人接走的插话」接着发——会话的 `drainPending`、子代理的 `runSubAgent` 都认这条路。

人说了新话会结束上一个 skill 的工具限制，否则会以一个他未必记得的 skill 名义，静默拒绝他刚要求
的工作。第一轮要把发起这次运行的那条提示也算上：状态表活得比一次运行长。

## 工具说「到此为止」

`ToolResult.terminate` 曾经一直存在却没人写也没人读，唯一需要它的 `yield` 只能靠模型自觉收尾。
`yield` 的语义是交付即结束：结果已经在 `state` 里，此后再问一句，答案没人读。

那一句的代价不是零。顺利时是一整份上下文换一句「我做完了」；不顺时模型无话可说、服务商转成一个
没有内容的流，就是一次空回答，而空回答会被重试。开着无限重试时这一轮永远转下去：真实日志里量到
过同一个请求重发 222 次、34 分钟。收在 `turn_end` 之后：这一轮完整发生过，只是不再问下一句。
出错的 `yield`（校验没过）不算终止，那是「重填一次」。

## 重复：先纠正，纠正无效才停

这里原本是「问满六次就结束」。停下来既没告诉模型该怎么办，也没把等结果的人放出来，只是把一次
卡住变成一次中断。现在：

- **第三次起不再重贴原文**，只回一句「这是第 N 次，结果没变」。真实日志里同一段 `read` 贴过 5 遍，
  同一个 `skill` 注入过 4 次，每次 5,625 token。只换给模型看的那份，工具照常执行——结果真变了，
  指纹就不同，根本走不到这里。
- **原文必须真的还在眼前。** 计数只在改动工作区、压缩时清零，而剪枝会把早先那几份换成回查指针；
  那时再把这份也换掉，模型手里一份原文都没有，所以这份留着。
- **换在提交之后。** 日志和界面留原文，代价是重启后重建的历史在这条上和当时发出去的不同，前缀从
  这里断一次。换到提交之前，要么等整批跑完才落盘（崩溃时丢掉已完成的结果），要么让计数看到的
  不是原文，都不划算。
- **两条线两句话。** 对一个每轮都在改 `offset` 的调用说「你用了同样的参数」，模型对照一眼就知道
  不成立，连带后半句一起不信。真实记录里一次翻了 37 页的搜索全程没收到提示，收到时那句话描述的也
  不是它在做的事。
- **`RepetitionWatch` 跨整条续跑链共用一只**，由调用方给。每次调用新建一只，计数在续跑时清零：
  真实日志里那个会话跑了 588 轮、起停五次，每一段都以为自己是第一段。

阈值和误伤记录见 `repetition.ts` 顶部和
[agent-cost-and-stopping.md](agent-cost-and-stopping.md)。

## 单个请求里的几件小事

- **重试按请求计数。** `fetchWithRetry`（拿连接）和 `retryStream`（保连接）嵌套，各自从 1 数，
  直接透传时屏幕上数成 1、2、1、1、2，第五次尝试被叫成「第 1 次」。人在等的是这个请求。
- **`retry_settled` 必须说。** 它是唯一同时知道「重试了几次」和「最后那条什么样」的地方；少了它，
  「正在重连」没有下文，「重连成功」和「窗口闲着」长得一样。一次都没重试过的**失败**（密钥错、
  模型名错，分类器判 `fatal` 当场停）也要说，否则界面上只剩一片安静。
- **前缀指纹**写在回复上，作为缓存未命中的归因证据（`ai/prefix-fingerprint.ts`）。基准只从缓存
  诊断也算数的请求推进（`requestPrompt`），两边比的是同一对请求。
- **`AgentRunResult.view`** 是模型眼里的整段历史（压缩、剪枝之后）。子代理续跑从它往后接，前缀才
  逐字相同；从转录重建会丢掉压缩边界、挪动日期块，缓存从第二条起全部作废。
- **`session.environment`** 给主会话用：它的历史每轮从日志重建，日志里没有日期块；渲染只看消息自己的时间
  戳，同一份历史每次得到同样的字节。子代理不开，它存的就是带日期块的 `view`。
