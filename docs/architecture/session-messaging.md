# 会话之间的消息

在跑的会话之间可以互相发现、发消息、等对方做完拿回结果。用的是模型，不是人：工具只给模型，界面上
没有给人发消息的入口。照的是 t3code 的线程工具（`t3_thread_send` / `t3_thread_wait`）。为什么这样
设计见 [ADR-0040](../adr/0040-session-messaging.md)。

## 谁和谁能通信

- **只认在跑的会话。** 在跑的是主进程 `session-hub.ts` 那张表里已经起来、没在退场、没在删的会话。
  没起来的历史会话看不见，也不会被叫醒。侧聊、子代理、CLI 都不参与。
- **目录要重叠。** 每个会话的目录 = cwd + 所在项目的全部源目录 + （cwd 是链出去的 git worktree
  时）主工作树。两个会话的目录里有一对相同、或一个包含另一个，就互相看得见。比较前一律过
  `pathKey`（软链、`/var` 与 `/private/var`、Windows 大小写），包含判断用 core 的 `pathWithin`。
  代码在 `electron/peer-reach.ts`。
- **对方权限比自己宽，不能发。** `ask` < `auto` < `full`，取两边叠加了项目层之后的
  `settingsInEffect.permissionMode`。防的是一个要审批的会话被拒之后，请一个不审批的会话代劳。反过来
  可以：宽的请窄的做事，窄的那边每一步照样走自己的审批。代码在 `electron/peer-policy.ts` 的
  `broaderThan`。

## 地址

`名字 [ref]`：名字是会话标题（没有就用目录名），ref 是 id 的前六位。名字会变、会重名，ref 不变，
所以解析时 ref 优先；重名又没带 ref 时不猜，把候选列出来。代码在 `electron/peer-address.ts`。

## 模型手里的工具

| 工具 | 做什么 |
| --- | --- |
| `list_sessions` | 列出能联系的会话：地址、忙闲、权限模式、cwd |
| `send_message({ to, message, mode? })` | 发一条消息：对方闲着就开一轮；忙着时默认排到它手上这件事之后，`mode: "steer"` 才插进去 |
| `wait_for_session({ to, timeout_seconds? })` | 等收到我那条消息的那一次运行结束，它最后那段话作为这次调用的结果回来 |

三件都标了 `sessionOnly`，子代理拿不到。由 `session-hub.ts` 通过 `extraTools` 注入每个会话，状态全
在路由器里（`electron/session-peers.ts`）。工具说明和每一种退回的报错写在 `electron/peer-tools.ts`，
报错都说清下一步怎么做。

## 一条消息怎么走

```
send_message ─▶ 路由器（electron/session-peers.ts）
                 ├─ 解析地址、查目录重叠
                 ├─ 对方权限比自己宽：退回
                 ├─ 限速 / 去重 / 链长（electron/peer-policy.ts）
                 └─ AgentSession.receive ─▶ SessionDeliveries 攒 400ms
                                              ├─ 闲着：开一轮
                                              ├─ 忙着、queue（默认）：排到这一轮之后，另开一次运行
                                              └─ 忙着、steer：插进这一轮，下一个请求读到

wait_for_session ─▶ 钉住收到那条消息的那一次运行（electron/peer-runs.ts）
                    ├─ 那次运行结束：带回它最后那段话、怎么收的场
                    ├─ 对方在等它的人回答：当场返回，同一件只报一次
                    ├─ 消息还没进对话就被停下：说消息丢了
                    └─ 人对发件方开口 / 超时 / 本轮被停 / 对方关了 / 互相等
```

进对话的是一条 `synthetic` 的 user 消息，带 `peer` 字段（`core/src/types/message.ts`）。给模型读的
正文由 `core/src/runtime/peer-letters.ts` 拼：开头一段说明这不是用户说的话、不构成授权、做完把结果
写在这一轮最后一条回复里；每条消息套 `<session-message from="名字 [ref]" cwd="…">`。界面上画成一行
（`PeerLetterRow`），点开读全文、一下跳到发消息的会话。对收到的一方，这是一件新的事，开新的一轮
（`grouping.ts` 的 `opensTurn`）。

`fromPerson: false`：消息不是人开口，不放开正在等的子代理，也不清技能限制。

**消息不替代审批。** 收件方因为一条消息去做的每一件事，照常走它自己的审批。

## 等待

等的是**收到我那条消息的那一次运行**，不是对方下一次空闲。对方正忙着人交代的事、或同时有别的会话
找它时，下一次空闲之前它可能跑了好几次，最后一句回答的是别人（照 synara 的 `wait_for_threads`）。

- 一次运行 = `agent_start` 到 `agent_end`。hub 把每个会话的事件都交给路由器（`observe`），
  `peer-runs.ts` 记下每封消息（带 `id`）的 `message_start` 落在哪一次：在跑就算这一次，闲着就算
  下一次。开轮之前就被停下的只有 `agent_end`，当作刚开就结束的一次，收场是 `aborted`。
- 结果是那次运行最后一段 assistant 文本，最多 4,000 字；截掉的部分告诉模型「请对方写进文件」。
- 对方在等它的人审批或回答问题时当场返回，让发件方去告诉人；同一件只报一次，再等就等到它被答完。
- 消息还在 400ms 里攒着就被对方的人按了停：消息跟着丢掉，答「丢了」，不拿它上一句冒充答复。
- 没给对方发过消息就等：照 t3code，闲着立刻返回它最后那句，忙着就等手上这一次。
- 默认等 600 秒，最多 1,800 秒。到点只是不等了，对方照常干。
- **人对发件方开口就不再等**：插话只在两次请求之间才有人读，等待会把人说的话压到对方做完为止。
  工具经 `ctx.untilSpokenTo`（core 的 `DelegationWaits.until`，和 ADR-0029 等子代理是同一套）
  当场交回；渲染进程看到主会话在 `wait_for_session` 上时，人说的话直接插进去而不是排队
  （`awaitingSession`）。
- 发件方这一轮被人停下，`ctx.signal` 让等待立刻返回。对方在等待中被卸载，答「已关闭」。
- 互相等：路由器记着谁在等谁，顺着走回到自己就直接退回。

发件方要结果就自己等，所以运行时不需要再递「它闲了」的回执，收件方也不需要再发一条消息回来——
那样会多开一轮去读一件已经知道的事。

## 防失控

都是确定的判断，拦下来时的报错告诉模型下一步怎么做：

| 规则 | 值 | 报错让它做什么 |
| --- | --- | --- |
| 单条长度 | 20,000 字符 | 写进文件，发路径 |
| 链长 | 28 跳 | 停止转手，交回给人 |
| 同一会话在链中 | 10 次 | 同上 |
| 同一对之间重复正文 | 30 秒内 | 不再发 |
| 令牌桶（按发件→收件） | 容量 30，每秒补 0.5 | 合成一条，或先等对方做完 |
| 互相等 | 顺着「谁在等谁」走回自己 | 先把自己那部分做完 |

链：每条消息带经手的会话 id。收件方接着这条消息再发出去的，链往后接；人在那个会话里开口之后，它
发的是一条新链。

20,000 这个上限是先定的：一条消息全文进收件方的上下文，超过这个量就该写文件。有了真实用量之后用
`pnpm audit:sessions` 量一次再调。

## 没有做的

- 给人用的入口（输入框里 @ 一个会话附上地址、叫醒点过名的会话）：这是模型之间的协作，人要交代
  另一个会话做事，直接去那个会话说。
- 冲突自动检测（「两个会话改了同一个文件就通知」）：没有可靠的信号，t3code 也没有做。模型自己发现
  文件在底下被改了，可以 `list_sessions` 找到是谁、发消息协调。
- 侧聊不参与：它本来就不碰工作区，要动手的事交给主会话。
- 跨进程（CLI、多实例）没有通路：桌面端是单实例，路由放在主进程就够了。
- 不兼容 Claude Code 的会话：它的 socket 协议没有公开，带版本号，随时会变。
