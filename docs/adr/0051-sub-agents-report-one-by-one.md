# ADR-0051：子代理派出即放手，跑完一个送回一个

- 状态：已采纳
- 日期：2026-10-14
- 取代：[ADR-0029](0029-parent-lets-go-when-spoken-to.md) 第 2 条（只在人开口时放手）和「没有做的」第一条（不把 `task` 改成一直异步）
- 相关：core `runtime/sub-agent/delegation-waits.ts`（`dispatch`、`outstanding`、`deliveryMessage`）、
  `runtime/sub-agent/exit-cut.ts`、`runtime/sub-agent/sub-agent-restore.ts`（`cutByExit`）、
  `runtime/session.ts`（`idle`、`submit`、`revert`）、`runtime/session-deliveries.ts`（`outstanding`）、
  `runtime/turn-config.ts`（`spawnSubAgent`）、`tools/task.ts`；cli `src/run.ts`；desktop
  `electron/notify.ts`、`electron/session-hub.ts`、`src/features/conversation/DeliveryRow.tsx`

## 背景

ADR-0029 之后，`task` 默认同步：父会话等到子代理交差，只有人插话时才放手。并行派三路时，人看到的是
主智能体一声不吭地等最慢的那一路，三路的结论最后挤在一段话里出来。

用户拿另一个 agent 的截图对照：每回来一路，对话里就出现「消息来自 子代理 ›」，主智能体就着这一路说
一段——已经知道了什么、还在等哪几路。我们把两种做法摆成可以播放的样张放在一起对比（同一个场景：三路
分别在 2s、4s、6s 回来，最后一路出错），用户选了这一种。

## 决定

1. **派出即放手。** `DelegationWaits.dispatch` 当场交回「已派出，在后台跑」：结果会作为消息送回来，
   不用等、不用查、不用 `resume`，不要重派或自己去做它的活；手上没有别的事，就一两句话告诉用户派了
   什么、结束这一轮。还没上名单就被拒的（不认识的类型、续跑不了的 id）照旧当场作为工具错误交回。
2. **一个一份送达，先到的点名还在等谁。** 送达仍然攒 400ms（前后脚回来的合成一轮）。送达消息末尾分
   两种：还有没回来的，就点名是哪几个，只叫它就这几份说清带来了什么、不写最终回答；都回来了，叫它把
   全部结论（包括之前送到的）合并成一份按问题组织的回答。
3. **派完收尾不算闲。** `AgentSession.idle` 把还在后台跑的子代理算进去。等「闲了」的那几方——
   `wait_for_session`、会话归档、闲时压缩、命令行——都在最后一个送回来、那一轮做完之后才往下走。
   撤回（`revert`）之后重新看一次：撤掉的派发不再送回来。
4. **命令行等到全部送达。** `cli/src/run.ts` 在第一轮之后 `whenIdle()`；最后那一轮说的才是回答。
5. **系统通知等最后一个回来。** 派完的那一轮、中间每一次送达的那一轮收尾时，后台还有子代理在跑，
   就不报「完成」。
6. **退出时还在跑的，重开后告诉主会话。** 从前 `task` 挂着，退出后那次调用记成「Plume 退出时还在跑」，
   续跑的 id 就在里面；现在那条结果早就是「已派出」了。重开会话时，从日志里认出派了、没送回过结果、
   又没有 `subagent_done` 的那几个；人下一次开口时，在他那句话前面补一条送达，说清它被退出打断了、
   上下文还在、怎么续跑。不在打开会话时自动开一轮：人还没开口，替他花钱去接一件他未必还要的事不对。
7. **送达在对话里是题注。** 「消息来自 @谁 · 任务 ›」，和来信、后台命令同一个骨架（`FlowRow`），落在主
   智能体随后那段话上面；出错的在行尾标红；点一下面板翻到它那一页。从前它是一颗带底色的胶囊按钮，
   一轮回来三个就是三颗，比主智能体自己的话还显眼。

## 代价

- **每次送达多一次请求。** 三路分开回来，主会话发 5 次请求（派、派完那句收尾、三次送达），同步等待是
  2 次（派、拿到结果后回答）——实测见 desktop `e2e/subagent-one-by-one-demo.ts`。每次都重发一遍前缀；
  缓存命中的话这部分按缓存价计，没命中就是原价。攒送达的 400ms 只能合并前后脚的。
- **每段话只能就已经回来的判断。** 后回来的可能推翻先回来的；送达末尾那句「不要写最终回答」就是为此。
- `pnpm audit:sessions` 读的是历史日志，改前改后两次输出没有可比的变化：这一项要在新会话积累起来之后，
  对照「每个派发会话的主会话请求数」和缓存命中率再看一次。

## 没有做的

- **不做「父会话可以选择等」的开关。** 两种语义并存，模型每次派之前都要先判断用哪种，而判错的代价不对称：
  该等的选了不等只是多一轮，不该等的选了等就回到了 ADR-0029 之前那种一声不吭。
- **不给子代理加「中途汇报」。** 一路一份送达已经是这个粒度；子代理自己说到一半就往回送，父会话每次
  都要多开一轮。
- **退出打断的不自动续跑。** 见决定第 6 条。
