# ADR-0044：计划模式是会话上的一个开关，只读靠执行期拒绝，计划是方案不是清单

日期：2026-10-11

状态：已采纳

## 背景

Plume 的权限只有 ask / auto / full 三档。想先看清楚再动手，只能派 `plan` 子代理：它只读、交一份
结构化计划，但它读过的东西留在它自己的历史里，主会话拿到计划后要照着再读一遍才能动手。人也没有
一个「这一轮别改东西」的开关——full 下模型看完就改，ask 下每一次读都要点头。

ZCode、maka、codex 都有计划模式。三种做法：codex 只在提示词里说「别改」，模型会忘；ZCode 在
执行期按 `mode.plan.nonReadOnly` 拒绝，批准后的计划写进固定文件、压缩后重新注入；maka 用一个
结构化的 `SubmitPlan` 工具把计划交给人审。

## 决定

**开关记在会话上**（`SessionMeta.planMode`），不做成第四档权限。计划和权限是两件事：「计划中 +
完全访问」是成立的组合（看的时候不要每次点头，批准后也不要）；权限是全局的，一个对话进计划模式
不该让别的窗口跟着进去。`/plan` 切换，桌面端输入框旁有同一个开关。

空白对话还没有会话可写，开关先记在渲染进程（`draftPlanMode`），第一句话建会话时随 `sessions:create`
写进初始 meta。不能建完再补：第一轮按建出来的 meta 装工具表，补上的开关要到第二轮才生效，而第一轮
是照常跑的。也不落到全局设置，理由同上。

**只读靠执行期拒绝，工具表一字不改**（`runtime/plan-mode.ts`）。每个工具的 name / description /
parameters 原样留着，只在 `execute` 外面包一层：开关开着时，不在只读名单上、又没明说
`mutating: false` 的调用直接返回一条拒绝，告诉它去调 `submit_plan`。不裁工具表的理由是前缀缓存：
工具定义排在请求最前面，批准之后要把写工具还给模型，表一变整段前缀作废——子代理 `7831f70c` 在
检查点换表那一次，355,790 token 按原价重算，就是这个代价。名单而不是「没标 `mutating` 就放行」，
和沙箱「拿不到约束就拒绝」（ADR-0004）同一个方向。

- `bash` 只放行 `isReadOnlyCommand` 认得的命令，而且压进只读沙箱跑：按文本认命令会认错，认错一次
  的代价由沙箱兜住。要提权的一律拒绝。
- `lsp` 只拒 `rename`，其余是查询。
- `task` 放行：子代理拿到的是同一张包过的表（`turn-config.ts` 从这一轮的 `tools` 派生），管事的
  开关是主会话的那一个。`submit_plan` 是 `sessionOnly`，子代理交不了计划。
- MCP 工具看它自己报的 `mutating`；没报的拒绝。

**计划经审批通道交给人**（`runtime/plan-tool.ts`）。`submit_plan` 只收一个参数 `plan`：
整份计划，一段 Markdown，和 `plan` 子代理的输出是同一份。它发一张 `interactive` 审批卡片，正文是渲染好的计划，
两个选项「批准，开始执行」「要改」，允许自定义输入。full / auto 和「总是允许」都不会替人批准
计划——这是在问人要不要这么做，不是在问权限。

- 批准：**同一轮里**把状态图里的开关关掉，包着的 `execute` 立刻放行，模型不用等下一轮；工具结果带 `details: { kind: "plan", plan }`，这条结果提交
  时会话把 `SessionMeta.planMode` 清掉，下一轮从 meta 读到的也是关着的。
- 「要改」或自定义文字：当作反馈回给模型，开关不动，它接着改计划。
- 什么都没说（取消卡片）：`terminate`，这一轮结束，人说下一句。

**桌面端：计划在右栏读，卡片只管拍板。** core 的选项不变，桌面端不按业务提问那样画选项列表，而是
一张两行的卡（`PlanApproval`）：标题、「打开计划」，一排「拒绝 / 修改… / 接受」，逐项询问档下多一颗
「接受并开启自动模式」（先把全局权限档切到 auto 再批准；已是 auto 或 full 时不给，免得把 full 降档）。
Esc 是修改，⌘↵ 是主按钮，⇧⌘↵ 是接受。

计划交上来时右栏自动打开一个「计划」标签（`dock/panels/PlanPanel.tsx`，每份计划只开一次，人关了不追），
整份计划按 Markdown 摊开；划一段字就地留评论，评论用 CSS Custom Highlight 在原文上画下划线，不改
`Markdown` 画出的 DOM，那段字最后一个字的右上角挂一枚圆形序号。评论本身不列在面板里，列在审批卡上：有评论
卡片就进修订态，评论按正文先后编号（和面板上的序号同一个数）、带引文和删除，下面一个「还有什么要补充的吗？」，
一排「拒绝 / 接受 / 修订」。「修订」把补充的话和评论（`> 引文` + 评论）拼成一段反馈发回去，走的还是上面
「自定义文字」那一条；模型改完重交是新的一次审批，评论清空。评论只放渲染进程内存（`store/plan-review.ts`），
审批一结束面板转只读。窄窗口右栏一次只摆一格，开面板会盖住卡片，所以那时不自动开，正文画在卡里。

**有评论时接受，评论作为注意事项随批准交出去，不打回。** 原先接受只发「批准」，划过的评论悄悄作废，人以为
模型看到了；而多数评论是「做的时候注意」，为它重写一整份计划是白花一轮。审批的回答多一个 `note` 字段
（`ApprovalDecision`，审批闸门校验它是字符串、去掉首尾空白），选项仍是「批准」；`submit_plan` 把它存成
`ApprovedPlan.notes`，`renderPlan` 末尾多一节「执行时注意」。工具结果、计划面板、压缩快照读的都是这一份，
所以注意事项跨压缩也在。要按评论改计划本身，走「修订」。

**计划面板的正文从会话历史里读，不另存。** 交计划的调用和它的结果本来就在会话日志里，面板读最后交上来的
那一份（`currentPlan`，`@plume/core/plan-view`，渲染进程可用的子入口），批准的、打回的都算，面板上标
「已批准」「未批准」；压缩以后调用不在了，读快照里批准的那份。所以重启、换会话回来计划都还在。这场对话交过
计划以后，顶栏「面板」菜单、右栏「+」和命令面板里一直列着「计划」，没交过就不列。评论仍只放内存——它只对
一次进行中的审批有意义。

**计划是方案，不是清单。** 最初计划是一串有序步骤，批准时原样写进 `TODOS_KEY`。这样一来计划只能按执行粒度写，
人审到的是一串动作，看不出改动前是什么样、打算怎么验；模型执行时也改不了拆法，因为清单就是计划。现在计划里
没有步骤，批准时不碰清单，工具结果提醒模型：三步以上的活，在第一个动作里用 `todo_write` 自己拆。codex 也是
这么分的：`update_plan` 是清单，计划模式交的是 `<proposed_plan>`，两者明确不混用。

**计划是一段 Markdown，不拆字段。** 中间试过一版六栏（现状、方案、改动、验证、风险、未确定），每份计划都被套进
同一张表，三行的小改动也得填满，读起来像表格而不是方案。现在和 codex 的 `<proposed_plan>` 一样：要写什么由提示词
说——标题、概要、主要改动、测试、假设，通常三到五节——怎么写由模型按这件事的大小定。

**计划跨压缩不丢**。批准的计划进 `task-context`（`CompactionContext.plan`），和原始请求、清单同一个
槽，压缩后以「User-approved plan (execute it; re-plan only if the user says so)」原样重新注入。
不另写文件：Plume 已经有一个压缩后保留运行时事实的位置，再加一个文件是两处真相。

**提示词只在开着时多一段**（`PromptSource` 的 `plan`）。参照 codex 的计划模式提示词，这一段写明：现在只读，
让它去做也只是去规划；代码查得到的事实自己查；意图、范围、取舍上会改变计划的选择，交之前用 `ask_user` 问清，
给选项、给推荐，跳过就按推荐走并记成假设；执行的人没有要做的决定了才交 `submit_plan`；改动按行为或子系统分组，
只在能防错时写路径；打回以后交一份完整的替换。这一段要明说通用准则里「有合理理解就照做、说明假设」在计划模式
不适用——不说的话模型两条一起读，拿不准的都当成假设直接交，从来不问。关掉这段就没了——它跟着会话 meta 走，不进冻结的前缀。

## 不做的

- **不裁工具表。** 理由同上；而且把 `edit` 从表里拿掉，模型在计划里写「第三步改 x 文件」时看不到
  这个工具长什么样。
- **不只靠提示词。** codex 的做法。「别改」说一次，三十轮后模型顺手改一个 typo 是常事。
- **不做成权限档。** 权限是全局、持久的；计划是一个对话里的一个阶段。
- **不替人批准。** full 也要点一下。计划模式的全部意义是「动手之前人看一眼」。

## 后果

- 计划模式里 `task` 派出去的 `general` 子代理也改不了文件；它会收到同一条拒绝。想要子代理只读调研，
  本来就该派 `explore` / `plan`。
- `bash` 的只读名单（`isReadOnlyCommand`）管得严：`git status` 过，`pnpm test` 不过。计划阶段跑测试
  要人批准后才行。这条放宽前要先看沙箱兜不兜得住。
- 批准后有没有清单取决于模型自己写不写。续跑（`continueWhileWorkRemains`）按清单判断还有没有活，
  没写清单的长任务撞到步数上限就会停下，和没有计划模式时一样。批准结果里那句提醒就是为了这个。
