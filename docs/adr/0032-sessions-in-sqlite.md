# ADR-0032：会话存进一个 SQLite 库，流式回复边写边落盘，删会话不删账

- 状态：已采纳
- 日期：2026-09-30
- 相关：`packages/core/src/session/{db,store,storage,apply-record,replay-records,spend,partial}.ts`；`packages/core/src/runtime/session-log.ts`（`PartialWriter` 接在 `message_start` / `message_update` 上）；desktop `electron/usage-scan.ts`、`electron/session-cleanup.ts`；`scripts/session-dump.ts`

## 背景

会话原来是 `~/.plume/sessions/<projectId>/<id>.jsonl` 加一份 `index.json` 索引，旁边还有 `usage-ledger.jsonl` 记不属于任何会话的花销、`<id>.display.json` 缓存展示结果。几处毛病都出在「一份事实存了好几份」上：

- 索引要整份重写，和删除、重建、新建之间反复出过竞态（新建的会话不在列表里、删掉的会话被一次更新写回来），每一种都要一条专门的测试守着。
- 回复只在 `message_end` 才写进日志。进程在流式输出中途没了，这一轮已经收到的几分钟输出全部丢失。
- 用量页从会话日志里汇总花销，删掉一条会话，它花过的钱也从总额里消失，设置页的数字就对不上服务商的账单了。
- 移动会话要把文件在两个目录之间搬，搬一半失败时两边的状态都得处理。

参考了 maka（SQLite，流式部分分段落盘、刻意保留删除会话的花销）和 ZCode 的做法。项目还没上线，用户明确要求**整体换掉，不做迁移、不兼容旧数据**。

## 决定

1. **一个库：`~/.plume/sessions/sessions.db`。** 用 Node 自带的 `node:sqlite`（Electron 43 / Node 24 都有），不加依赖。五张表：`sessions`（每条会话一行，带当前 meta）、`records`（只追加的记录，`(session_id, seq)` 唯一）、`partials` / `partial_chunks`（正在流式输出的回复）、`spend`（每一次计费调用）。
2. **每条记录连同它引起的一切在一个事务里写完。** 读当前 meta、算下一个 `seq`、插记录、更新 `sessions` 行、写花销、清掉已提交回复的流式残留，都在 `BEGIN IMMEDIATE` 里。调用方手里的 meta 过期了也没关系，事务里读到的才算。这样原来的写队列、索引重建和它们的竞态整个没有了。会话已经被删掉时，迟到的写入什么都不提交、`append` 返回 `null`，桌面端的观察层据此不再广播，删掉的会话不会被一次迟到的标题或用量写回侧边栏；这条记录里已经计费的调用照样写进 `spend`。
3. **历史不改写。** 撤回仍然是一条 `truncate` 记录，读的时候跳过被作废的尾巴；`sinceSeq` 增量读取的契约不变。
4. **流式回复边写边落盘。** 第一段文字立刻写，之后每 80ms 或攒够 8KB 写一次，只写每个块新增的尾巴（不重写整段）。回复提交时在同一个事务里删掉残留；被丢弃的回复直接删。读到一段写入者已经不在的残留（写它的进程死了；最后一次写入早于本次开机——断电重启后旧 pid 可能已归别的进程；或者本进程里已经没人在写），就把它当成「按了停止」的那条回复提交进去（`stopReason: "aborted"`），只留文字和思考，丢掉写了一半的工具调用。时间戳记成它最后被写入的时刻，不是打开它的时刻。一轮在流式中途抛了异常（没有 `message_end`），轮次结束时就地按同样的规则提交并通知窗口，不留给下一轮去删。正常退出时先把还没写出的那一批写完，再关库。某一批写失败（库忙、磁盘出错）时它留在内存里、排在后来的内容前面，报一次错、定时重试，流式输出本身不因此中断；回复的最终写入成功之后才放下流式状态，失败时这条回复不进内存里的转录，残留还在，轮次收尾时按「停止」提交。每次开始流式都生成一个 token 记在残留上，追加、丢弃、回复提交时的清理都只认这个 token：同一会话开了新的流，旧写入者（同进程或别的进程）再写、再删、再提交都碰不到新的那一段；只比 pid 拦不住同一进程里的旧写入者。
5. **花销单独一张表，删会话不动它。** `spend` 没有外键，删会话、清理一段时间都不碰它；fork 复制过来的历史标记 `copy`，不重复计费。压缩和撤回也各记一行边界，缓存诊断按请求序列读的时候知道哪里是有意打断的。用量页按 `spend.id` 增量读、每次最多 5000 行一页，缓存里同时记下库的标识（`info` 表里建库时生成的随机 id）：库被挪走重建或从备份恢复后行号从头编，标识对不上就从头读。
6. **打不开就报路径，不自动重建。** 打不开可能只是被锁、或者同步盘拷了一半，自动重建会把所有会话清空。桌面端启动时先试开一次，打不开就弹窗说出路径和原因然后退出——否则窗口会一直停在加载中；结构版本和这个版本的 Plume 不一样的库（不论新旧）也走这条，不做迁移，移走后重新打开会建一个新的。
7. **删除后立刻归还空间。** `auto_vacuum = INCREMENTAL`，每次删除后跑 `incremental_vacuum`，否则「清理」之后文件一点都不会变小。vacuum 搬动的页都经过 WAL：实测删掉 320MB 后 `-wal` 涨到 313MB、而且不会自己缩，库变小了磁盘没变。所以删除后再做一次 `wal_checkpoint(TRUNCATE)`，平时用 `journal_size_limit`（16MB）限住 WAL。vacuum 是删除的主要耗时（2026-10-01 实测：320MB 约 0.5s，1GB 约 1.7s，都占着主进程）；拆成 `incremental_vacuum(N)` 分步、中间让出事件循环，最长一次停顿仍有 150–670ms，总耗时却变成三倍，所以仍是一次做完。
8. **删除先占位再删。** 删单条、删归档、按时间清理都走主进程的 `deleteSessions`：先把会话标成「删除中」，停掉它，删掉行，最后才撤掉标记；这期间 `ensureLiveSession` 对它一律返回空，新请求被拒绝而不是在一条马上消失的会话上跑起来。按时间清理不是冲着某一条去的，所以先排除还有活在跑的（回合、刚提交、正在启动、侧边聊天正在打开或在答、后台任务、子代理），这一步和占位在同一个同步步骤里；删单条和删归档是冲着它去的，在跑的照样停掉，正在打开的侧边聊天读完存档发现主会话已经没了，就不再装上。

## 没有做的

- **不迁移旧的 `.jsonl`。** 还没上线，按用户要求直接换掉。旧目录留在原地，应用不再读它。
- **不开第二个连接、不放到工作线程。** `node:sqlite` 是同步 API，会占住主进程。2026-09-30 本机实测：一次追加 p50 0.04ms、p99 0.26ms、最慢 1.9ms；5000 条消息（每条 2KB）的会话整条载入约 22ms；1000 批流式残留写入共 25ms。流式输出时的写入远在一帧 16ms 之内；打开一条特别长的会话会占住主进程一两帧，只在打开那一下。等有真实会话量到卡顿再挪。

## 后果

- 用 `cat`、`grep` 直接看会话不行了，用 `pnpm dump:session <id>` 倒出来，形状和以前的 `.jsonl` 一样。
- `~/.plume` 不能在应用开着的时候放进同步盘：库旁边的 `-wal` 文件和库本体必须一起拷。换机器前先退出应用——正常退出会关库，WAL 并回库文件后删掉，这时只拷 `sessions.db` 就够了。
- 按天的「活跃会话数」来自记录表，删掉的会话不再算活跃；花销来自 `spend`，删掉的会话照样算。两者口径不同是有意的。
- `pnpm audit:sessions` 读的是库；和换库之前跑出来的结果没有可比性（旧会话没有迁移过来）。
